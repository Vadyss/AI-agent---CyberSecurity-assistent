# Run event stream

Every run is described by an ordered stream of events. The same events arrive over the WebSocket (`/api/v1/ws`) and from `GET /api/v1/runs/{run_id}/events?after_seq=N`. This document is the reference for the event payloads, their order and how a client builds state from them. HTTP endpoints, request bodies, error codes and the sign-in behaviour are specified by [api/openapi.json](api/openapi.json); [FRONTEND_CHANGES.md](FRONTEND_CHANGES.md) lists what changed in the API after the first (unversioned) version, including the `queued` and `cancelled` statuses and the `run_cancelled` event, which are not repeated here.

The payload examples in section 6 are validated by the backend test suite (`backend/tests/unit/test_models.py`).

## 1. Conventions

- JSON, UTF-8, `snake_case` field names.
- Times are ISO 8601 strings in UTC with milliseconds, for example `2026-10-04T14:30:12.345Z`.
- A field without `| null` is always present and never `null`.
- Text generated by the application for people (`message`, `reason`, `description`, `steps`, `explanation`, `summary.text`, error messages, violation details) is in English. Analyst text and raw logs are never translated.

## 2. Untrusted fields

Fields marked **[untrusted]** come from the language model, from logs or from the analyst. They can contain anything, including HTML, scripts and text that looks like an instruction. A client must render them as plain text (never as HTML or Markdown), let long unbroken strings wrap, and decide nothing from their wording: only `passed`, `status` and the event type are authoritative. The approve button is only a request; the backend decides.

Test strings a client must display literally: `<img src=x onerror=alert(1)>`, `<script>alert(1)</script>`, `**bold** [link](javascript:alert(1))`, and 300 `A` characters without a space.

## 3. Limits

| What | Format or limit |
|---|---|
| `run_id` | `^run_[a-z0-9]{4,32}$` |
| Skill and rule names | `^[a-z][a-z0-9_]{2,49}$` |
| `request` | 1 to 2000 characters |
| Approval `comment`, rejection `reason` | 0 to 500, 1 to 500 characters |
| `message` (event envelope) | at most 200 characters |
| `summary.text`, `explanation` | at most 1000 characters |
| `error_excerpt` | at most 500 characters |
| Skill `description` | at most 300 characters |
| `plan_ready.steps` | at most 10 items of at most 200 characters |
| `violations[].detail` | at most 200 characters |
| `code_sha256` | 64 lowercase hexadecimal characters |

The backend enforces them: longer input is rejected and model text is truncated.

## 4. Shared types

### 4.1 SkillInfo

| Field | Type | Description |
|---|---|---|
| `name` | `string` | Skill name, format above |
| `version` | `int` | Version, from 1 |
| `kind` | `string` | `parser` \| `aggregation` \| `enrichment` |
| `description` | `string` | Description; **[untrusted]** for agent-built skills |
| `origin` | `string` | `seed` (shipped with the app) \| `agent` (built by the agent) |
| `status` | `string` | `candidate` (awaiting approval) \| `installed` (in the registry) |
| `created_by_run` | `string \| null` | Run that built it; `null` for seed skills |
| `created_at` | `string` | Time it was created or copied into the registry |

### 4.2 Metrics

| Field | Type | Description |
|---|---|---|
| `true_positives` | `int` | Attacks caught |
| `false_positives` | `int` | False alarms |
| `false_negatives` | `int` | Attacks missed |
| `precision` | `float \| null` | 0 to 1; `null` when `true_positives + false_positives = 0` |
| `recall` | `float \| null` | 0 to 1; `null` when `true_positives + false_negatives = 0` |
| `thresholds` | `object` | `{ "min_precision": float, "min_recall": float }` |
| `passed` | `bool` | Decided by backend code against `thresholds`, never by the model |

Clients show `null` as "—".

### 4.3 Recipe

An `object`, entirely **[untrusted]** because the model wrote it. Clients do not parse it: they show `name` (always present) as the title and the whole recipe as formatted JSON, so the recipe format can change without a client change. Example:

```json
{
  "name": "ssh_password_spraying",
  "parser": "ssh_parser",
  "filter": [{ "field": "outcome", "op": "eq", "value": "failure" }],
  "aggregation": {
    "skill": "distinct_count_window",
    "params": { "group_by": "src_ip", "distinct_field": "user", "window_s": 300 }
  },
  "condition": { "field": "distinct_count", "op": "gte", "value": 5 }
}
```

### 4.4 RunStats

| Field | Type | Description |
|---|---|---|
| `duration_ms` | `int` | Run length from `run_started` to `summary` |
| `llm_calls` | `int` | Number of model calls |
| `cost_usd` | `float \| null` | Sum of valid non-negative provider-reported `usage.cost` values, including retries; `null` if no response reported a cost |
| `tokens_total` | `int \| null` | Total tokens; `null` if the provider does not report them |
| `skills_built` | `int` | Candidates created in the run |
| `skills_reused` | `int` | Skills reused from the registry |

The cost covers provider-reported values only, not an estimate from token counts and not hosting. A numeric zero is a valid cost and differs from the unknown cost `null`. The mock model returns `null`.

## 5. Event envelope

Every event has the same shape:

| Field | Type | Description |
|---|---|---|
| `type` | `string` | Event type (section 6) |
| `run_id` | `string` | Run it belongs to |
| `seq` | `int` | Order within the run, starting at 1, without gaps |
| `timestamp` | `string` | Time of creation |
| `phase` | `string` | `intake` \| `plan` \| `forge` \| `rule` \| `validation` \| `approval` \| `done` |
| `message` | `string` | Short description for the timeline, built from templates in backend code but possibly containing model-chosen names, so **[untrusted]** |
| `data` | `object` | Content by type; `{}` for types without data |

```json
{
  "type": "skill_candidate_ready",
  "run_id": "run_8f3a",
  "seq": 9,
  "timestamp": "2026-10-04T14:30:12.345Z",
  "phase": "forge",
  "message": "Skill distinct_count_window passed tests (attempt 2 of 3).",
  "data": { }
}
```

Clients ignore unknown event types and unknown fields.

## 6. Event catalog

### 6.1 Phase `intake`

#### `run_started`

- `request`: `string` **[untrusted]**

```json
{ "request": "Detect password spraying on SSH." }
```

### 6.2 Phase `plan`

#### `plan_ready`

Sent only for a valid plan. An invalid plan raises `policy_rejected` with `target: "plan"`.

- `steps`: `string[]` **[untrusted]**
- `skills_needed`: `string[]`, skill names

```json
{
  "steps": ["Parse the SSH logs", "Count distinct users per IP in 5 minutes", "Alert above the threshold"],
  "skills_needed": ["ssh_parser", "distinct_count_window"]
}
```

#### `skill_reused`

One event for each registry skill the plan uses.

- `skill`: `SkillInfo` (always `status: "installed"`)

```json
{
  "skill": {
    "name": "ssh_parser", "version": 1, "kind": "parser",
    "description": "Turns OpenSSH auth.log lines into events.",
    "origin": "seed", "status": "installed",
    "created_by_run": null, "created_at": "2026-10-04T12:00:00.000Z"
  }
}
```

#### `capability_missing`

Sent only when something is missing.

- `skills`: list of `{ "name": string, "description": string }`; `description` **[untrusted]**

```json
{ "skills": [{ "name": "distinct_count_window", "description": "Count of distinct values of a field in a window, per group." }] }
```

### 6.3 Phase `forge`

Repeated for each missing skill, one after another.

#### `forge_started`

- `skill`: `string`, name
- `attempt`: `int`, 1 to 3
- `max_attempts`: `int`, always 3

```json
{ "skill": "distinct_count_window", "attempt": 1, "max_attempts": 3 }
```

#### `skill_tests_failed`

- `skill`: `string`
- `attempt`: `int`
- `tests_total`: `int`
- `tests_failed`: `int`
- `error_excerpt`: `string` **[untrusted]**

```json
{ "skill": "distinct_count_window", "attempt": 1, "tests_total": 6, "tests_failed": 2, "error_excerpt": "AssertionError: expected 3, got 2" }
```

#### `skill_candidate_ready`

- `skill`: `SkillInfo` (always `status: "candidate"`, `origin: "agent"`)
- `attempt`: `int`
- `tests_total`: `int`
- `code_sha256`: `string`

```json
{
  "skill": {
    "name": "distinct_count_window", "version": 1, "kind": "aggregation",
    "description": "Counts distinct values of a field in a time window for each group.",
    "origin": "agent", "status": "candidate",
    "created_by_run": "run_8f3a", "created_at": "2026-10-04T14:31:02.000Z"
  },
  "attempt": 2,
  "tests_total": 6,
  "code_sha256": "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"
}
```

### 6.4 Phase `rule`

#### `rule_drafted`

Sent right after the model's proposal, before the gatekeeper checks it, so the timeline also shows a recipe that the gatekeeper then rejects.

- `attempt`: `int`, 1 to 3
- `max_attempts`: `int`, always 3
- `recipe`: `Recipe`
- `explanation`: `string` **[untrusted]**

```json
{
  "attempt": 1,
  "max_attempts": 3,
  "recipe": { "name": "ssh_password_spraying", "parser": "ssh_parser" },
  "explanation": "Looking for IP addresses that try many different users within 5 minutes."
}
```

The recipe is shortened in the example; the full shape is in section 4.3.

#### `rule_evaluated`

- `attempt`: `int`
- `dataset`: `string`, always `"tuning"`
- `metrics`: `Metrics`

```json
{ "attempt": 1, "dataset": "tuning", "metrics": { "true_positives": 10, "false_positives": 4, "false_negatives": 4, "precision": 0.71, "recall": 0.71, "thresholds": { "min_precision": 0.9, "min_recall": 0.9 }, "passed": false } }
```

### 6.5 Phase `validation`

#### `validation_done`

- `dataset`: `string`, always `"validation"`
- `metrics`: `Metrics`

```json
{ "dataset": "validation", "metrics": { "true_positives": 9, "false_positives": 0, "false_negatives": 1, "precision": 1.0, "recall": 0.9, "thresholds": { "min_precision": 0.9, "min_recall": 0.9 }, "passed": true } }
```

### 6.6 Phase `approval`

#### `summary`

- `text`: `string` **[untrusted]**
- `stats`: `RunStats`

```json
{
  "text": "I built the distinct_count_window skill and the rule caught every attack in the tuning set.",
  "stats": { "duration_ms": 48210, "llm_calls": 7, "tokens_total": 18340, "skills_built": 1, "skills_reused": 1 }
}
```

#### `voice_ready`

Optional. It can arrive any time after `summary`, even after `awaiting_approval`, or never.

- `audio_url`: `string`, always `/runs/{run_id}/audio` relative to the API base

```json
{ "audio_url": "/runs/run_8f3a/audio" }
```

#### `awaiting_approval`

Contains everything the approval panel needs.

- `recipe`: `Recipe`
- `metrics_tuning`: `Metrics`
- `metrics_validation`: `Metrics`
- `new_skills`: `SkillInfo[]` (status `candidate`; may be empty)

```json
{
  "recipe": { "name": "ssh_password_spraying", "parser": "ssh_parser" },
  "metrics_tuning": { "true_positives": 14, "false_positives": 1, "false_negatives": 0, "precision": 0.93, "recall": 1.0, "thresholds": { "min_precision": 0.9, "min_recall": 0.9 }, "passed": true },
  "metrics_validation": { "true_positives": 9, "false_positives": 0, "false_negatives": 1, "precision": 1.0, "recall": 0.9, "thresholds": { "min_precision": 0.9, "min_recall": 0.9 }, "passed": true },
  "new_skills": []
}
```

### 6.7 Phase `done`

#### `skill_installed`

Only after approval. One event for each skill in `new_skills`.

- `skill`: `SkillInfo` (always `status: "installed"`)

#### `rule_approved`

- `rule_name`: `string`
- `comment`: `string | null` **[untrusted]**

```json
{ "rule_name": "ssh_password_spraying", "comment": null }
```

#### `rule_rejected`

- `reason`: `string` **[untrusted]**

```json
{ "reason": "Too many false positives." }
```

### 6.8 Events in any phase

`phase` in the envelope is the phase in which they happened.

#### `policy_rejected`

The gatekeeper rejected something. One attempt is used up. The run continues with the next attempt or ends with `run_failed`.

- `target`: `string`, `plan` \| `skill` \| `recipe`
- `name`: `string | null`, skill or rule name; `null` for a plan
- `attempt`: `int`
- `violations`: list of `{ "code": string, "detail": string }`; `detail` **[untrusted]**

Violation codes are an open list; clients show any code. Examples: `FORBIDDEN_IMPORT`, `FORBIDDEN_CALL`, `INVALID_MANIFEST`, `INVALID_NAME`, `UNKNOWN_SKILL`, `RECIPE_INVALID`, `RECIPE_EXCEPTION`.

```json
{
  "target": "recipe",
  "name": "ssh_brute_force",
  "attempt": 1,
  "violations": [{ "code": "RECIPE_EXCEPTION", "detail": "The filter excludes src_ip 10.0.0.5." }]
}
```

#### `run_failed`

End of the run.

- `reason_code`: `string`, one of:
  - `REQUEST_REJECTED`: the gatekeeper refused the request
  - `PLAN_INVALID`: not even the third plan passed
  - `FORGE_FAILED`: a skill failed even on the third attempt
  - `RULE_FAILED`: the rule missed the thresholds even on the third attempt
  - `VALIDATION_FAILED`: the rule failed on the validation set
  - `LLM_ERROR`: the model API failed
  - `SANDBOX_ERROR`: the sandbox failed
  - `QUOTA_EXCEEDED`: the tenant's model budget was used up
  - `INTERNAL_ERROR`: another backend error
- `reason`: `string`, description from the backend

```json
{ "reason_code": "FORGE_FAILED", "reason": "Skill distinct_count_window failed tests after 3 attempts." }
```

### 6.9 Usage in any active phase

#### `llm_usage`

Emitted after each model request attempt, including transport retries, length retries and JSON repairs. It does not change run status. It is stored and broadcast under the same sequence rules as other events.

- `kind`: `"call"` or `"summary"`.
- `record`: the content-free call record below, or `null` for a summary.
- `totals`: running or final totals; `steps` has each step's calls, retries, cost and percentage share.
- `summary`: `null` for a call; at completion it holds `totals`, `most_expensive_step`, `average_cost_usd`, `average_run_count` and one to three `observations`.

```json
{
  "kind": "call",
  "record": {
    "run_id": "run_example",
    "call_id": 1,
    "step": "planner",
    "iteration": 1,
    "attempt": 1,
    "model": "anthropic/claude-sonnet-5.5",
    "input_tokens": 1000,
    "cached_tokens": 200,
    "output_tokens": 100,
    "total_tokens": 1100,
    "cache_write_tokens": 0,
    "cost_usd": "0.00264",
    "cost_source": "provider",
    "currency": "USD",
    "duration_ms": 1500,
    "timestamp": "2026-10-09T12:00:00.000Z",
    "estimated": false,
    "retry": false,
    "status": "success",
    "warning": null
  },
  "totals": {
    "calls": 1,
    "total_tokens": 1100,
    "known_tokens": 1100,
    "cost_usd": "0.00264",
    "known_cost_usd": "0.00264",
    "unknown_cost_calls": 0,
    "estimated_calls": 0,
    "calculated_cost_calls": 0,
    "retries": 0,
    "steps": [
      {
        "step": "planner",
        "calls": 1,
        "retries": 0,
        "cost_usd": "0.00264",
        "share_percent": "100.0"
      }
    ]
  },
  "summary": null
}
```

`iteration` is the role's proposal attempt; `attempt` is the network attempt within that call; `call_id` identifies each distinct request within the run. JSON repair is marked `retry: true`, even when its network attempt resets to 1. Examiner repairs also advance `iteration`. Each record counts as at most one retry.

Token values come from provider usage. Unreported splits and cache counts are `null`, not invented. When no usable token counts are returned, an offline UTF-8 byte tokenizer supplies a conservative estimate and sets `estimated: true`; unavailable output on transport failures stays `null`. Real totals are never replaced by estimates. Cached tokens are a subset of input tokens, and reasoning tokens are already included in provider completion totals. No prompt, completion or reasoning text is stored in usage records.

Money in this event is an exact non-negative decimal **string** in USD, or `null`. `cost_source` is `provider`, `pricing`, `mock` or `unknown`. Provider `usage.cost` takes precedence; calculations from published rates are labelled estimates. Missing or ambiguous rates yield `null` and a warning. `status` describes HTTP success or error, not parsing or gatekeeper acceptance. The cost is inference cost: provider plan markup and relay hosting are excluded.

A total is `null` if any call's corresponding value is unknown. `known_cost_usd` and `known_tokens` are explicit subtotals, never full totals. Percentages and the most expensive step are unavailable when any step has an unknown cost. Averages use saved runs whose model work is complete and whose costs are known; `average_run_count` states the denominator. Final usage is emitted before `summary` and `awaiting_approval`, or before `run_failed`, because no later approval action calls a model. It is also saved to `<DATA_DIR>/tenants/<tenant id>/runs/<run_id>/usage.json` after every call and at completion.

## 7. Order and states

### 7.1 Phases

Phases always go in the order `intake` → `plan` → `forge` → `rule` → `validation` → `approval` → `done` and never go back. `forge` is skipped when nothing is missing.

### 7.2 Start and end

- Every run starts with `run_started`.
- Every run ends with exactly one of `rule_approved`, `rule_rejected`, `run_failed` (or `run_cancelled`, see [FRONTEND_CHANGES.md](FRONTEND_CHANGES.md)).
- After the terminal event no further event of that run arrives, except a possible `voice_ready`.

### 7.3 Plan

1. An invalid plan raises `policy_rejected` (`target: "plan"`). After the third invalid plan, `run_failed` with `PLAN_INVALID` follows.
2. A valid plan raises `plan_ready`, then `skill_reused` for each registry skill, and finally `capability_missing` if something is missing.

### 7.4 Forge (for each missing skill)

1. `forge_started` with attempt *n*.
2. Then exactly one of: `policy_rejected` (`target: "skill"`), `skill_tests_failed`, or `skill_candidate_ready`.
3. After a failure with *n* < 3, `forge_started` with attempt *n* + 1 follows. After a failure on the third attempt, `run_failed` with `FORGE_FAILED` follows.

### 7.5 Rule

1. `rule_drafted` with attempt *n*.
2. Then exactly one of: `policy_rejected` (`target: "recipe"`), or `rule_evaluated`.
3. When the gatekeeper rejected the recipe or `rule_evaluated` has `passed: false`: with *n* < 3 the next `rule_drafted` (attempt *n* + 1) follows; with *n* = 3, `run_failed` with `RULE_FAILED`.
4. When `rule_evaluated` has `passed: true`, `validation_done` follows.

### 7.6 Validation and approval

1. `validation_done` with `passed: false` leads to `run_failed` with `VALIDATION_FAILED`. There is no retry.
2. `validation_done` with `passed: true` leads to `summary`, then `awaiting_approval`.
3. After approval: `skill_installed` for each skill in `new_skills`, then `rule_approved`.
4. After rejection: only `rule_rejected`. Candidates are discarded.
5. `voice_ready` has no fixed place.

### 7.7 Run status from events

| Last deciding event | `status` |
|---|---|
| `run_started` | `running` |
| `awaiting_approval` | `awaiting_approval` |
| `rule_approved` | `approved` |
| `rule_rejected` | `rejected` |
| `run_failed` | `failed` |

Other events do not change the status.

## 8. How a client builds state

1. Keep, per run, the list of events ordered by `seq` and the value `last_seq`. All panels read from this one store.
2. **Page load:** open the WebSocket first and buffer incoming events; call `GET /runs`; for each run call `GET /runs/{run_id}/events?after_seq=0`; merge history and buffer, dropping duplicates by `(run_id, seq)`; then load `GET /skills`. The WebSocket opens first so that no event is lost while history downloads.
3. **Every incoming event:** drop it if `(run_id, seq)` is known; create the run if `run_id` is unknown; if `seq` is greater than `last_seq + 1`, fetch the gap with `after_seq=<last_seq>` and merge; otherwise append it and raise `last_seq`.
4. **Connection loss:** reconnect after 1 s, then 2 s, 4 s, at most 10 s; after reconnecting repeat the history steps with `after_seq=<last_seq>`. A 404 `RUN_NOT_FOUND` for a run means the server no longer has it; remove it from the view.
5. A successful response to `approve`, `reject` or `POST /runs` only confirms receipt. State changes only through events. An error response is shown to the user.

## 9. Typical sequences

These assume the seed skills `ssh_parser` and `count_window`.

### Password spraying: the agent builds a new skill

`run_started` → `plan_ready` → `skill_reused` (ssh_parser) → `capability_missing` (distinct_count_window) → `forge_started` (1) → `skill_tests_failed` (1) → `forge_started` (2) → `skill_candidate_ready` (2) → `rule_drafted` (1) → `rule_evaluated` (1, `passed: false`) → `rule_drafted` (2) → `rule_evaluated` (2, `passed: true`) → `validation_done` (`passed: true`) → `summary` (`skills_built: 1`, `skills_reused: 1`) → `awaiting_approval` (`new_skills`: distinct_count_window) → `voice_ready` → *waits for approval* → `skill_installed` → `rule_approved`.

### Distributed brute force: the agent reuses the skill

One user, many IP addresses; the same skill `distinct_count_window` with different parameters. `run_started` → `plan_ready` → `skill_reused` (ssh_parser) → `skill_reused` (distinct_count_window) → `rule_drafted` (1) → `rule_evaluated` (1, `passed: true`) → `validation_done` → `summary` (`skills_built: 0`, `skills_reused: 2`) → `awaiting_approval` (`new_skills`: empty) → *waits for approval* → `rule_approved`.

### Prompt injection in a log

`run_started` → `plan_ready` → `skill_reused` ×2 → `rule_drafted` (1, recipe with an exception for one IP address) → `policy_rejected` (`target: "recipe"`, `RECIPE_EXCEPTION`) → `rule_drafted` (2) → `rule_evaluated` (2, `passed: true`) → `validation_done` → `summary` → `awaiting_approval` → *waits for approval* → `rule_approved`.

### Forge failure

`run_started` → `plan_ready` → `skill_reused` (ssh_parser) → `capability_missing` (distinct_count_window) → `forge_started` (1) → `skill_tests_failed` (1) → `forge_started` (2) → `policy_rejected` (`target: "skill"`, `FORBIDDEN_IMPORT`) → `forge_started` (3) → `skill_tests_failed` (3) → `run_failed` (`FORGE_FAILED`, phase `forge`).

## 10. Backend invariants

1. An event receives its `seq` under the run's lock, is stored first and sent over the WebSocket afterwards, so `GET .../events` always contains everything already sent.
2. Approve and reject check the state and change it atomically; of two concurrent requests only one succeeds, the other gets 409.
3. Skill names and run IDs are used in file paths, so they are validated against the patterns in section 3 before every use. An invalid skill name is a `policy_rejected` with `INVALID_NAME`; an invalid `run_id` in a URL is a 404.
4. Model text is truncated to the limits before it reaches an event, and `message` is built from templates, not from model output.
5. A slow WebSocket client must not delay a run: each client has a bounded queue, sends have a timeout, and a broken client is disconnected.
6. A `RECIPE_EXCEPTION` is any filter that excludes a specific identity, for example `neq` or `not_in` on `src_ip`, `user` or `host`; the exact rule is set by the gatekeeper policy.

## 11. Changing this document

Adding an event or a field is safe; renaming or removing anything is not. The catalog section is parsed by a test, so keep its heading structure.
